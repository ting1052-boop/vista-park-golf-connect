## 2. 확정 구성

**Agent는 사용 상태를 관찰하면서 관리자 정상 종료 명령을 실행한다. 예약이 없다는 이유로 무인제어를 제거하지 않는다.**

| 구성 | 담당 | 하지 않는 일 |
| --- | --- | --- |
| 공용 Windows Agent | PC heartbeat, 게임 실행 관찰, 이용 추정, 이벤트 보관/전송, 인증된 PC 정상 종료 | 예약·과금·입주민 인증, 게임 강제 복귀, 사용시간 만료 강제 종료 |
| VISTA 서버/대시보드 | 매장별 정책, 상태/집계, 권한 확인, 대상별 명령, 릴리스 정보 | 사설망 HA에 직접 접속하거나 heartbeat 부재를 전원 OFF로 단정 |
| 상시 매장 제어기 + HA | 매장/구역 스케줄 실행, WOL, 연결된 프로젝터 제어 | Agent 이용 추정으로 임의 전원 차단 |
| PC 초기화/세팅 도구 | 최초 등록, 해당 타석 자격증명 설정, 검증된 Agent 설치, 자동실행 설정 | Agent 감지 로직의 별도 복제, 모든 타석 토큰 내장 |
| 별도 업데이트 실행기 | 다운로드 검증, 기존 Agent 정상 중지, 교체, 재실행, 롤백 | 게임 프로세스 종료, 이용 중 강제 교체, 업데이트마다 토큰 재발급 |

단일 EXE를 유지한다. 송도 프로필에서만 관찰형 운영을 활성화하고 시흥의 세션/잠금/라운드 감지 동작은 보존한다. monitorOnly는 고객용 잠금 UI를 사용하지 않는다는 기존 의미를 유지하며, 관리자 전원 제어 금지를 뜻하지 않는다.

송도는 PC 9대, 물리 타석 8개다. 골프 6번은 A-06 우타와 A-07 좌타 PC로 구성한다. 전원 제어와 인증은 PC별로 분리하며 A-06/A-07 토큰을 공유하지 않는다. 물리 타석 이용 여부는 둘 중 하나 이용 신호가 있으면 이용 중으로 합칠 수 있지만 사람 수 중복 제거는 하지 못한다.

## 3. 화면과 이용 판정

게임 관측 상태와 이용 추정 상태를 별도 필드로 유지한다. 한쪽을 보기 좋게 만들려고 다른 쪽을 덮어쓰지 않는다.

### 파크골프

- 큰 START 버튼이 있는 최초 화면: 화면을 확인한 경우 `대기 중`.
- START 다음 모드 선택 화면: 고객 입장으로 간주하고 이용창 시작. 코스나 1홀 진입까지 기다리지 않는다.
- 스트로크/자유연습/코스 이동: 같은 시간대 이용창 유지. 다시 세지 않는다.
- 일반 코스 확인 + 홀 미확인: `일반 코스`만 보조 표시. 모드 자체를 모르면 일반 코스라고 만들지 않는다.
- 홀 OCR은 필수 기능에서 제외한다. 홀 인식 실패가 이용창을 없애면 안 된다.

구현 선택: 먼저 현장 로그에서 START 화면과 모드 선택을 반복 구분할 수 있는지를 확인한다. 현재 menu 하나로 두 화면을 분리할 수 있다고 확정하지 않는다. 고유 로그가 없으면 개인정보 없는 고정 UI 영역의 로컬 화면 판독을 시험한다. START 버튼과 모드 선택의 긍정적 특징을 각각 확인하며 START가 안 보인다는 이유만으로 입장 판정하지 않는다. 캡처 실패/가림/다른 모니터/해상도 변경은 unknown이다. 이미지나 원본 로그는 서버에 보내지 않는다.

게임 창 새 입력을 파크 임시 감지로 쓸 수는 있지만, 이를 START 진입 정확 감지와 동일하다고 주장하지 않는다. 정밀 감지가 검증되지 않은 파일은 시험판으로만 제공한다.

### 골프 연습장

1단계는 대상 게임 창의 새로운 사용자 입력을 이용 신호로 사용한다. 드라이빙 레인지와 스트로크 모두 같은 방식이다. 사용자 허용대로 간단한 입력으로 시작할 수 있으나 실제 타구·재실·고객 신원 확인은 아니다.

프로그램 실행만으로 시작하지 않는다. 최초 스냅샷은 기준점이며 과거 입력으로 시작하지 않는다. 게임 외 앱 입력은 제외한다. 최소한 연속 관측에서 대상 창이 유지됐는지와 입력의 신선도를 확인하고, 폴링 방식의 오탐이 남으면 이벤트 시점 대상 창을 확인하는 입력 관찰 또는 로컬 타이머 판독으로 보완한다. 키 내용은 수집하지 않는다. 클릭 3회 감지가 구현된 것처럼 설명하지 않는다.

원격으로 게임을 조작하는 관리자도 사용 신호를 만들 수 있다. 유지보수 중 감지/집계 일시중지 기능과 표시가 필요하며, 중지해도 heartbeat와 정상 종료 명령은 작동해야 한다.

## 4. 정시간 이용창

최신 사용자 지시인 **매 정시부터 다음 정시까지**를 송도 정책으로 채택한다. 과거 시작 후 60분 설명은 대체한다.

- 시간대: Asia/Seoul. 예: 10:00~11:00, 11:00~12:00.
- 10:12에 최초 사용 신호: 실제 감지 시작은 10:12, 종료 예정은 11:00, 남은 시간은 48분이다. 11:12까지 늘리지 않는다.
- 10:00에 사용 신호: 11:00 종료. 정시 도착만으로 이용을 만들지는 않는다.
- 입력/홀 이동/짧은 부재/Agent 재시작은 종료 예정시각을 변경하지 않는다.
- 11:00에 관찰창만 만료한다. 게임 화면/PC/프로젝터에는 아무 명령도 보내지 않는다.
- 다음 시간대는 경계 이후 발생한 새 유효 입력/입장 이벤트가 있어야 시작한다. 전 시간의 playing 상태나 입력을 재사용하지 않는다.
- 파크가 계속 경기 화면에 남아 있으면 경계 이후 게임 창의 새 입력을 추정 신호로 사용할 수 있다. 이를 새 고객 입장으로 부르지 않는다.
- 새 입력도 화면 근거도 없으면 `이용 신호 대기`다. 최초 START 화면으로 돌아갔다거나 물리적으로 빈 타석이라고 주장하지 않는다.
- 같은 PC·정시간 구간은 집계 1회. 프로그램 재실행/복귀/재입력으로 같은 구간을 다시 세지 않는다. 재개 이력은 진단용으로 따로 남길 수 있다.

slotStart/slotEnd, 실제 최초 신호 startedAt, 마지막 관측시각을 구별한다. 현장 시계 오차는 서버시각과 비교하고 큰 오차/역행은 진단 오류로 처리한다. 오래된 이벤트는 수신일이 아닌 실제 발생일 KST에 귀속한다.

이는 아파트너 이용권한이나 정확한 60분 사용을 강제하는 기능이 아니다. 뒤늦게 입장한 사람도 다음 정시까지만 관찰한다는 운영 해석이며, 향후 시간제가 달라지면 매장 정책을 바꾼다.

## 5. 표시와 집계

카드의 대표 상태·KPI·상세는 동일 판정 결과를 쓴다. 운영 정책은 서버의 인증된 매장/타석 설정에서 결정하고 limitedMenu, A-01 문자열, 호스트명만으로 송도를 판별하지 않는다.

| 근거 | 대표 표시 |
| --- | --- |
| 유효한 현재 구간 이용창 + 최근 Agent 신호 | 이용 중 (상세: 입력/입장 신호 기준 추정) |
| 이용창 활성, 홀 또는 상세 게임 로그만 실패 | 이용 중 유지. 상세에 감지 저하 표시 |
| 최초 START 화면을 긍정적으로 확인 | 대기 중 |
| 구간 만료 후 새 신호 없음, 실제 화면 미확인 | 이용 신호 대기 |
| 처음부터 판단 불가 또는 Agent 신호 만료 | 상태 확인 불가 / 연결 확인 필요 |
| 게임 미실행을 확인 | 프로그램 미실행. 빈 타석 보장 아님 |

감지 건강 상태와 이용창 상태는 독립적이다. 과거 유효 신호는 해당 구간까지 보존할 수 있지만, Agent 연결이 끊겼으면 실시간 이용 확정처럼 표시하지 않는다. 종료 명령의 접수/실행 결과와 실제 PC 꺼짐도 구별한다.

집계 명칭은 `오늘 이용 감지 N회`로 한다. 의미는 사용 신호가 있었던 PC별 정시간 구간 수다. `오늘 이용자 N명`, 예약 수, 실제 타구 시간, 라운드 수가 아니다. 사람의 교대나 A-06/A-07 좌우 이동은 자동 식별하지 못한다. 물리 타석 집계가 필요하면 별도 지표로 정의한다.

## 6. 무인제어 경계

- 골프 켜기: A-01~A-06. 골프 끄기: A-01~A-07.
- 파크 켜기/끄기: P-01, P-02. 골프와 별도 시간표.
- 예약 세션이 없어도 타석/구역/매장 제어 가능. 타 매장 ID나 토큰으로 명령 수신/완료 처리 불가.
- PC 정상 종료는 Agent, WOL/프로젝터는 제어기와 HA. 이용 추정 만료는 전원 제어를 실행하지 않는다.
- 수동 종료는 이용 신호가 있으면 재확인. 정기 마감은 승인된 시간표 정책을 적용하며 관찰창 때문에 무기한 연기하지 않는다.
- Agent에는 별도 마감 스케줄을 중복 설치하지 않는다. 기존 HA 전체 기상/Windows 종료/BIOS RTC는 현장 확인 후 승인된 항목만 조정한다.
- 파크 종료 요청 21:30과 원장의 운영 조회 21:20 차이는 이번에 변경하지 않는다.
- 게임 강제 종료나 /f를 기본 정책으로 추가하지 않는다. Windows 종료가 막히면 실패/확인 필요로 보고한다.

## 7. 설치 및 서버 배포

설치와 업데이트는 구분한다. **처음 설치할 때만** 등록 창구에서 매장/타석을 등록하고 해당 PC 토큰을 받는다. EXE 업데이트 때는 기존 토큰을 보존한다. 기존 installAgent:true 등록 API는 토큰을 재발급할 수 있으므로 단순 업데이트용으로 호출하지 않는다.

신규 표준 실행 위치는 `C:\ProgramData\VISTA\agent\bin\VISTA-Bay-Agent.exe`, 설정은 `C:\ProgramData\VISTA\agent`로 통일하는 설계를 채택한다. 이는 아직 현재 설치기에 반영되지 않았다. 기존 LOCALAPPDATA/C:\VISTA 설치는 실행경로와 자동실행을 조사한 후 한 번의 설치 마이그레이션으로 옮긴다. APPDATA의 이용창/outbox는 동일 Windows 사용자 기준 보존한다. 설정 덮어쓰기나 토큰 없는 공용 패키지로 기존 인증이 사라지면 안 된다.

실행파일·업데이트 설정은 관리자만 수정할 수 있는 ACL로 보호한다. Agent는 게임을 보는 로그인 사용자 세션에서 한 번만 실행한다. SYSTEM 세션에서 입력/화면을 관찰하려 하지 않는다. 권한이 필요한 파일 교체는 별도 제한된 업데이트 작업이 담당한다. 토큰 읽기 권한은 실제 실행 계정으로 제한하고 서버 응답/로그/공개 배포물에 비밀값을 남기지 않는다.

배포는 기존 GitHub Releases 같은 HTTPS 파일 호스팅 + 서버의 승인 릴리스 정보 경로를 재사용한다. Vercel 함수에 EXE를 넣지 않는다. 파일 이름만 latest로 덮어쓰지 않고 버전별 불변 URL, SHA-256, 빌드 commit, 지원 설정/서버 버전을 기록한다. 새 버전 번호는 기존 태그와 대조해 부여하고 같은 버전을 재사용하지 않는다.

### 단계별 업데이트

1. 감지/이벤트 결함 수정, 깨끗한 checkout 빌드, 서버 계약 검증 후 시험 릴리스 생성.
2. 승인받은 추가형 DB migration과 API/대시보드를 먼저 배포. 구버전 Agent를 계속 수용.
3. P-01/A-01에만 수동 또는 설치 도구로 시험판 적용. 서버에서 버전/빌드/타석과 정상 신호 확인.
4. 시험 통과 후 stable 포인터를 변경하고 나머지 PC 확대. 이 단계만으로 기존 실행 중 Agent가 자동 교체되지는 않는다.
5. 자동 업데이트 지원 Agent/교체기를 최초 1회 설치한 뒤부터, 승인된 버전만 자동 다운로드/검증/교체할 수 있게 한다.

현재 0.9.8은 1~3단계 중 로컬 구현·검증까지만 끝난 상태다. `src/lib/agent-release.ts`는 실제 GitHub 릴리스가 아직 없으므로 0.9.6을 가리키게 그대로 두었다. 0.9.8을 현장에 배포하려면 릴리스 업로드와 SHA/URL 포인터 변경을 같은 배포 묶음으로 처리한다.

자동 업데이트 계약: 서명된 manifest(검증 공개키 고정), SHA-256, 허용 HTTPS 호스트, 버전/호환성 검사, 임시 파일 다운로드, 이전 EXE/설정 백업, 원자적 교체, 실행 실패 자동 복구. 서명 검증 없이 해시만으로 게시자의 진위를 보장한다고 설명하지 않는다. 네트워크 장애만으로 정상 새 버전을 무한 롤백하지 않는다.

기본 업데이트 시점은 새 게임을 실행하기 전 부팅 단계 또는 관리자가 승인한 유지보수 시간이다. 단지 입력이 잠시 없거나 이용 추정 창이 끝났다는 이유로 고객 이용 중인 PC를 교체하지 않는다. 안정 버전 배포 대상은 서버가 송도/시험 PC 단위로 제한한다. 임의 URL이나 임의 셸 명령을 내려보내는 업데이트 기능은 만들지 않는다.

## 9. PC 세팅 도구 개발자에게 전달할 시점

지금은 역할 경계만 공유한다: 세팅 도구는 서버의 승인 릴리스를 설치하며 Agent 감지 로직을 구현하지 않는다. 버전·URL·해시·설정 스키마·설치/업데이트 명령·성공 판정은 시험 릴리스 검증 뒤 한 번에 확정 전달한다. 존재하지 않는 다운로드 URL이나 아직 구현되지 않은 무인 설치 옵션을 미리 약속하지 않는다.

현재 다음 작업은 결함 수정과 P-01/A-01 시험판 준비다. 서버 파일 게시 자체보다 먼저 끝내야 한다. 이 문서의 설계 확정은 현재 EXE의 품질 인증이나 운영 배포 완료를 뜻하지 않는다.
