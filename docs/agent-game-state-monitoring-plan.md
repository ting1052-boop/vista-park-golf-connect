# Windows Agent 골프 프로그램 상태 감지 작업계획서

작성: 2026-09-12 / Codex. 상태: 프로세스 감지 MVP 구현 완료, DB 적용·배포·현장 활성화 대기.

## 1. 결론과 범위

추천은 **정확한 게임 프로세스 확인 + 제조사가 지원하는 읽기 전용 상태 정보**의 조합이다. 공식 API가 없다면 실제 플레이와 대응되는 로그를 검증하여 사용하고, 부족한 항목에만 창 제목·접근성 정보 또는 로컬 OCR을 적용한다. 지금은 자료가 부족하므로 홀 번호 감지가 가능하다고 확정할 수 없다.

우선순위 `공식 지원 → 로그·상태 파일 → 창 제목·UI Automation → OCR`은 타당하다. 다만 제조사 답변을 기다리는 동안 안전한 파일 목록·프로세스 조사는 병행한다. 모든 방법을 구현하지 않고, 한 PC의 조사 결과로 가장 단순하고 신뢰할 수 있는 한 가지 주 감지기를 선택한다. 제조사가 지원하는 이벤트 내보내기 기능이 있다면 화면 인식보다 우선한다.

이 기능은 관찰 전용이다. 라운드 종료를 감지해도 VISTA 예약, 요금, 남은 시간, 잠금, 세션 종료, 장비 전원을 변경하지 않는다. 게임을 켰다는 사실과 사람이 실제로 치고 있다는 사실도 구분한다. 여기서 `playing`은 게임의 라운드 진행 화면/상태이지 사람의 스윙을 확인했다는 의미가 아니다.

## 2. 현재 코드 분석

아래 경로는 저장소 루트 기준이다. 설치된 실행파일이 이 코드와 같은 버전인지는 현장 확인 필요.

| 위치 | 확인한 동작 | 계획에 미치는 영향 |
| --- | --- | --- |
| `windows-agent/package.json` | 버전 0.4.0, 기본 진입점 `electron-main.js`, Electron 의존성 `^31.0.0`, legacy 실행 별도 | Electron 경로를 우선 대상으로 한다. 설치본 버전과 패키징 방법을 별도 검증 |
| `windows-agent/electron-main.js`의 `runTasklist`, `isAnyGameRunning` | `tasklist.exe /FO CSV /NH` 결과에서 설정된 실행파일 이름 탐색 | 실행 여부만 알 수 있다. 조회 오류를 빈 문자열로 처리해 false가 되는 점을 향후 삼상값으로 분리 |
| 같은 파일의 `tick()` | 세션 조회 후 프로세스 조회를 기다리고 화면 모드와 heartbeat 처리 | 새 OCR/로그 처리를 이 경로에서 기다리면 안 된다. 독립 수집기의 최신 결과만 읽도록 계획 |
| 같은 파일의 `postHeartbeat()` | `gameAppRunning`, 세션 기반 `status`, 잔여시간 등을 Bearer 인증으로 전송 | 기존 필드 의미는 유지하고 별도 `gameTelemetry` 추가 |
| `windows-agent/vista-agent.js` | legacy 경로에도 tasklist 및 세션 기반 playing 존재 | 이번 MVP는 Electron만 지원, legacy는 감지 미지원으로 표시. 두 코드가 다 구현됐다고 보고하지 않음 |
| `src/app/api/agent/heartbeat/route.ts` | `gameAppRunning`을 타입에 받지만 저장하지 않음. Agent 접속시각과 kiosk 잠금·잔여시간 갱신 | 현재 서버에는 실제 게임 상태 저장 경로가 없다 |
| `src/lib/agent-server.ts`의 `touchAgent()` | `last_seen_at`, 버전, PC 이름 갱신 | 게임 관측시각과 접속시각을 따로 관리해야 함 |
| `src/app/api/agent/session/route.ts` | 세션 조회에서도 `touchAgent()` 호출 | 게임 감지 실패 중에도 PC 연결은 최신일 수 있음 |
| `src/lib/supabase/bays-server.ts`, 관리자 automation API/UI | Agent 최근 신호 기반 PC 연결 표시 | 게임 상태를 전원 상태나 타석 사용 여부 대신 사용하지 않음 |
| `supabase/migrations/202607020001_store_settings_extension_requests.sql` | `agent_devices`에 게임 상태 컬럼 없음, bay_id unique | 새 읽기 모델 필요. 실제 DB와 스키마 일치 여부는 구현 전 확인 |

현재 `status: playing`은 이용 세션과 잔여시간이 있다는 뜻이다. 이를 실제 골프 플레이로 재해석하거나 이름만 일괄 변경하지 않는다. `gameProcessNames`는 현장에서 확인한 게임 실행파일로 구성하고, Chrome이나 런처만 실행돼도 게임 실행으로 잡히는 설정은 피한다.

## 3. 첨부 화면에서 확인된 단서

사진은 플레이 화면이 아니라 `C:\PARK_260713-VISTA\Launch` 설치 폴더이다. `Logs`, `Launcher.exe`, `Tool.exe`, `save.ini`, `setting.ini`, `setting.json`, `SGEngine.dll` 등이 보인다.

- 먼저 `Logs`의 최근 파일과 실제 플레이 중 실행되는 프로세스를 확인한다.
- 런처가 다른 폴더의 게임을 실행할 수 있다. `Launcher.exe`가 실제 게임이라는 가정은 금지한다.
- 설정 파일이 보인다고 실시간 상태 파일인 것은 아니다. 수정시각 및 화면 전환과의 대응을 확인한다.
- `Foresight...`, OpenCV, DLL 이름만으로 제조사·제품·공식 SDK 지원을 추정하지 않는다.
- SQLite 파일이나 홀 정보가 존재한다는 증거는 아직 없다. DLL, PDB, 메모리 덤프 분석은 기본 조사 대상이 아니다.

## 4. 감지 방법 비교

평가는 이 제품에서의 실측이 아닌 일반적인 선택 기준이다. 정확도는 해당 정보가 실제 제공될 때 기준이며, 모두 현장 검증을 거친다.

| 방법 | 정확도·안정성 | 난이도 | 유지보수·업데이트 영향 | 개인정보 위험 | 판단 |
| --- | --- | --- | --- | --- | --- |
| 공식 API/SDK·이벤트 출력 | 의미가 문서화되면 높음, 연결 장애는 별도 처리 | 낮음~높음: 계약·SDK에 따라 다름 | 지원 버전 계약이 있으면 유리 | 고객·스코어 필드 제외 필요 | 최우선, 로컬 읽기 전용 선호 |
| 구조화 로그 | 실제 이벤트와 시점이 일치하면 높음 | 중 | 포맷·인코딩·회전 변경에 대응 | 이름·계정·경로 포함 가능 | 현실적인 우선 후보 |
| 로컬 상태 파일·SQLite | 최신 상태라면 높음, 저장 시점 지연 가능 | 중 | 스키마 변경·잠금·캐시 주의 | 계정·결과 DB일 가능성 | 제조사 허용 읽기 방식 확인 후 |
| 창 제목 | 필요한 값이 있을 때만 유효 | 낮음 | 제목·언어 변경에 민감 | 고객명이 제목에 포함될 수 있음 | 저비용 조사, 없으면 즉시 다음으로 |
| Windows UI Automation | 노출된 텍스트가 있으면 유리 | 중 | 접근성 제공자·컨트롤 변경 의존 | UI의 고객정보 읽기 제한 필요 | 읽기만 사용, 클릭·조작 금지 |
| 고정 영역 로컬 OCR | 화면·해상도에 따라 변동 | 중~높음 | UI 변경·DPI·가림·전체화면 영향 큼 | 화면 캡처 위험, 좁은 영역만 처리 | 부족한 필드의 최후 수단 |
| 프로세스·CPU/GPU 사용량 | 실행 확인에는 유용, 플레이·홀에는 낮음 | 낮음~중 | 로딩·백그라운드 작업으로 흔들림 | 비교적 낮음 | CPU는 진단 보조만, 플레이 판정 금지 |
| 네트워크 통신 분석 | 의미·암호화에 따라 불명확 | 높음 | 비공개 프로토콜 변경에 취약 | 인증·개인정보 노출 위험 높음 | 기본안 제외. 승인된 문서화 통신만 재검토 |

UI Automation은 대상 프로그램이 접근성 정보를 제공해야 유용하다. 사용자 정의 렌더링 화면에서 홀 텍스트가 노출되는지는 확인해야 한다. [Microsoft UI Automation 제공자 설명](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)

메모리 읽기/조작, DLL 주입, 후킹, 게임 변조, 인증서 우회, 패킷 재전송은 기본안에서 제외한다. 제조사가 명시적으로 지원하는 별도 계약이 없는 한 채택하지 않는다. 관측 목적에 비해 장애·지원 중단 위험이 크다.

## 5. 현장 사전조사: 비개발자용

손님 없는 타석 한 대에서 진행한다. 현재 Agent 설정이나 게임 설치파일은 수정하지 않는다. 운영 예약을 새로 만들 필요는 없으며, 유료 이용 테스트가 필요하면 별도 승인을 받는다.

1. 게임 화면의 제품명·버전을 적는다. 없으면 실행파일 우클릭 → 속성 → 자세히에서 제품명/파일 버전을 확인한다. 계정이나 라이선스 번호는 공유하지 않는다.
2. 제조사에 “실행/메뉴/라운드 진행/현재 홀/라운드 종료를 외부 관리 프로그램이 읽기만 할 수 있는 API, 로그, 상태 내보내기가 있는가?”를 문의한다. 사용 허용 범위, 지원 버전, 업데이트 안내도 확인한다.
3. 작업 표시줄 우클릭 → 작업 관리자 → 자세히에서 게임을 켜기 전후 새 실행파일을 비교한다. 의심 파일 우클릭 → 파일 위치 열기로 실제 위치를 확인한다. 종료나 작업 끝내기를 누르지 않는다. 어렵다면 개발자가 승인된 읽기 전용 프로세스 조사로 런처와 자식 프로세스를 구분한다.
4. 탐색기에서 `C:\PARK_260713-VISTA\Launch\Logs`를 열고 수정한 날짜 최신순으로 정렬한다. 파일명·확장자·크기·수정시각만 먼저 기록한다.
5. 아래 순서로 화면 상태와 시각을 적는다. 게임은 정상 메뉴로 조작하며 테스트 후 정상 종료한다. 각 단계에서 Logs의 수정시각과 크기가 달라지는지 본다.

| 시험 단계 | 기록할 것 |
| --- | --- |
| 게임 시작 전 | 실행파일 없음 여부, 기존 로그 수정시각 |
| 런처만 실행 | 게임 프로세스가 별도로 생기는지 |
| 메뉴/대기 | 해당 시각, 로그 변경 여부 |
| 첫 홀 시작 | 실제 표시 홀, 시각 |
| 다음 홀 이동 | 화면 홀과 로그 이벤트의 대응 |
| 일시정지·메뉴 복귀 | 라운드가 계속 유지되는지, 상태 값 차이 |
| 결과/라운드 종료 | 명시적 종료 표시 및 로그 이벤트 |
| 두 번째 라운드·게임 재시작 | 이전 홀 값이 남는지, 파일 교체 여부 |

6. 텍스트 로그는 작은 복사본을 메모장으로 확인한다. 원본에 저장하지 않는다. 이름·전화번호·토큰 등이 있으면 공유하지 말고 개발자에게 현장에서 필요한 이벤트 줄만 가려서 전달한다. 바이너리 파일은 억지로 열거나 변환하지 않는다.
7. 로그로 부족하면 창 제목이 상태별로 달라지는지 기록한다. UI Automation 조사는 개발자가 읽기 전용 검사 도구로 수행하며 일반 사용자는 설치/권한 변경을 하지 않아도 된다.
8. 마지막으로 홀 숫자·메뉴·결과 표시만 잘린 테스트 화면을 준비한다. 모니터 수, 복제/확장 여부, 해상도, Windows 배율, 전체화면 여부를 함께 기록한다. 고객 화면은 사용하지 않는다.

SQLite가 발견되어도 원본을 편집하거나 실행 중인 `.db` 하나만 복사하지 않는다. WAL 모드에서는 별도 파일에 최신 변경이 있을 수 있다. 개발자가 제조사 허용 읽기 전용 접근 또는 일관된 백업 방식을 검증한다. 잠금 발생 시 건너뛰며 journal mode 변경·WAL 삭제·강제 checkpoint를 하지 않는다. [SQLite WAL 설명](https://www.sqlite.org/wal.html), [백업 API](https://www.sqlite.org/backup.html)

현장 산출물: 제품/버전, 실제 실행파일, 상태별 시각표, 개인정보를 제거한 최소 로그 예시, 접근성 결과, 필요 시 잘린 테스트 화면. 전체 설치폴더·전체 로그 압축본·메모리 덤프는 요청하지 않는다.

## 6. 단계별 구현 계획과 선택 관문

| 단계 | 수행 내용 | 다음 단계 조건 |
| --- | --- | --- |
| 0. 조사 | 위 체크리스트, 제조사 문의, 설치 Agent 버전 확인 | 확인 가능한 필드와 근거를 표로 확정. 정보가 없으면 unknown MVP로 제한 |
| 1. 프로세스 MVP | 정확한 실행파일 식별, true/false/null 분리, 독립 수집기와 기능 플래그 | 프로세스 조회 실패가 기존 tick을 지연시키지 않음 |
| 2. 주 감지기 실증 | 공식 API 또는 로그/상태 파일 한 종류, 메뉴·홀·종료를 관측 | 개인정보 제거 테스트 자료로 화면과 반복 대응 확인 |
| 3. 서버·화면 | 선택적 telemetry, 현재 상태 저장, 두 관리자 화면에 같은 표시 규칙 | 구버전 Agent·감지 미지원·DB 장애 회귀 통과 |
| 4. 필요 시 OCR | 부족한 필드만 로컬 영역 인식, 화면 프로필별 테스트 | 정상·오류 화면에서 오판과 부하 기준 충족 |
| 5. 제한 배포 | 한 타석 관찰 모드 → 검증 후 나머지 | 운영자 확인 및 별도 배포 승인 |

예상 작업량은 조사 후 재산정한다. 초안은 조사 0.5~1일(제조사 회신 제외), 프로세스/서버/화면 MVP 2~4일, 로그 감지기 1~3일, OCR 추가 3~7일이다. 지원 데이터가 없는 경우 일정으로 해결 가능성을 보장하지 않는다.

수집기는 별도 자식 프로세스 등으로 격리하고, Agent는 마지막 정상화 결과만 비동기로 받는다. 읽기 시간 제한, 동시 실행 1개, 실패 시 중단·재시작 상한을 둔다. 게임 종료나 프로세스 재시작 시 이전 라운드 상태를 폐기한다. Electron main에서 무거운 OCR을 실행하지 않는다.

로그는 변경된 꼬리 부분만 제한적으로 읽고 파일 회전·잘림·부분 줄·인코딩·중복 이벤트를 처리한다. 옛 로그를 현재 세션으로 연결하지 않는다. 이벤트가 뜸한 로그는 완전한 상태 전이 규약과 연속성을 입증하지 못하면 최근 줄만으로 지속 플레이를 단정하지 않는다.

OCR은 대상 창/모니터와 홀 표시 영역을 명시적으로 선택한다. 전체 이미지가 캡처 API 메모리에 일시 생성될 경우 즉시 자르고 폐기하며 파일·서버로 내보내지 않는다. 가림, 검은 화면, 해상도 변경은 unknown이다. 범용 화면 AI나 클라우드 이미지 전송을 기본안에 넣지 않는다. Electron의 화면 캡처 API 존재가 이 게임의 전체화면 캡처 성공을 보장하지 않으며, 저장소 버전과 현장 테스트로 검증한다. [Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer/)

## 7. 전송 데이터 계약 제안

기존 heartbeat에 선택적 `gameTelemetry`를 추가한다. 아래는 가상 시험값이며 실제 고객·세션 데이터가 아니다.

```json
{
  "gameTelemetry": {
    "schemaVersion": 1,
    "sampleSequence": 42,
    "monitorInstanceId": "example-instance",
    "gameRunning": true,
    "gameState": "playing",
    "currentHole": 3,
    "roundStatus": "in_progress",
    "stateSource": "log",
    "confidence": "high",
    "observedAt": "2026-09-12T01:00:00Z",
    "fieldEvidence": {
      "gameRunning": { "source": "process", "confidence": "high", "observedAt": "2026-09-12T01:00:00Z" },
      "gameState": { "source": "log", "confidence": "high", "observedAt": "2026-09-12T01:00:00Z" },
      "currentHole": { "source": "log", "confidence": "high", "observedAt": "2026-09-12T01:00:00Z" },
      "roundStatus": { "source": "log", "confidence": "high", "observedAt": "2026-09-12T01:00:00Z" }
    },
    "reasonCode": null,
    "detectorVersion": "example-log-v1"
  }
}
```

| 필드 | 의미·값 |
| --- | --- |
| `gameRunning` | true=확인된 게임 프로세스 존재, false=정상 조회에서 부재 확인, null=설정 미확정/권한/조회 실패 |
| `gameState` | `unknown`, `not_running`, `menu`, `playing`, `paused`, `results`. loading은 필요성이 입증되면 확장 |
| `currentHole` | 확인된 정수 또는 null. 기본 18홀 같은 임의 범위 고정 금지, 게임/코스 규격 확인 필요 |
| `roundStatus` | `unknown`, `not_started`, `in_progress`, `completed`. 강제 종료는 completed가 아님 |
| `stateSource` | `none`, `process`, `vendor_api`, `log`, `state_file`, `window_title`, `uia`, `ocr`, `mixed` |
| `confidence` | `unknown`, `low`, `medium`, `high`; 보정 안 된 숫자를 확률처럼 표시하지 않음 |
| `observedAt` | 실제 관측 UTC 시각. 전송하거나 heartbeat를 받을 때 덮어쓰지 않음 |
| `fieldEvidence` | 서로 다른 필드의 출처·신뢰도·시각. 프로세스 확실성으로 홀 값을 확실하다고 승격하지 않음 |
| `reasonCode` | `unsupported`, `timeout`, `stale`, `conflict`, `capture_unavailable`, `unrecognized_format` 등 허용된 코드 |

high는 지원 버전·신선도·형식 검증을 통과한 직접 근거, medium은 실증된 반복 OCR 등, low는 단일 약한 후보다. low 값은 확정 화면에 표시하지 않는다. 상단 confidence는 확인된 의미 필드의 보수적 요약이고, 출처가 없는 필드는 개별 unknown을 유지한다. OCR 엔진 자체 점수는 이 등급과 동일하지 않다.

예: 프로세스만 확인되면 `gameRunning=true`, 나머지는 `unknown`/null, 해당 필드 출처는 none이다. 감지 중단 시 마지막 홀 숫자를 현재 값으로 재전송하지 않는다.

## 8. 서버 API·DB 변경 계획

MVP는 별도 빈번한 API를 만들기보다 현재 heartbeat에 선택 항목을 붙인다. 세션 정보와는 별도 검증·저장 경로로 분리한다.

1. `heartbeat/route.ts`에 telemetry 허용 스키마·크기 상한(초안 4KB)·enum·정수·시각 검증을 추가한다. 잘못된 telemetry만 무시하고 정상 기존 heartbeat 처리는 유지한다. 잘못된 JSON 자체는 기존처럼 오류 처리한다.
2. 인증 토큰에서 얻은 Agent/매장/타석만 사용한다. 본문의 임의 bayId로 다른 타석 상태를 쓸 수 없게 한다. telemetry 문자열을 UI HTML이나 실행 명령으로 사용하지 않는다.
3. `agent_devices`에 nullable `game_telemetry jsonb`, `game_telemetry_received_at timestamptz`를 추가하는 최소 확장안을 우선한다. MVP에 전 관측 이력 테이블은 만들지 않는다. 운영 DB 적용은 사용자 승인 후 별도 마이그레이션으로 진행한다.
4. 서버 수신시각은 서버가 기록한다. 중복 sequence는 관측시각을 갱신하지 않는다. 같은 monitorInstanceId 내 역순/중복을 조건부 갱신으로 차단한다. 재시작 인스턴스 교체 때 과거 관측 재전송을 금지하고 한 Agent 프로세스만 실행되게 한다. 시계 이상·인스턴스 충돌은 unknown으로 낮춰 표시한다.
5. 기존 `touchAgent()`는 telemetry를 수정하지 않게 유지한다. 게임 저장 실패 시 heartbeat/잔여시간 경로를 실패시키지 않고 제한된 진단 로그만 남긴다. 무기한 DB 대기를 피하도록 독립 저장에 제한 시간을 둔다.
6. 관리자 조회에 최소 telemetry만 포함한다. 기존 매장 권한 검사를 재사용·확인하고 anon/회원/다른 매장에서 조회 불가함을 테스트한다. 이 변경을 공개 클라이언트 쓰기 권한 확대에 이용하지 않는다.
7. `bays-server.ts`, dashboard 및 automation API의 DTO와 UI를 동일 정상화 함수로 연결한다. DB 컬럼 미적용·구버전 Agent는 '게임 감지 미지원'으로 처리한다.

향후 감사 이력이 필요할 때만 상태 전이 이벤트 테이블을 추가하고 보존 기간을 정한다. 원본 로그나 매 샘플 이미지를 DB에 저장하지 않는다. 현재 서버 heartbeat의 기존 세션 갱신 로직 개선은 별도 과제로 두며 이번 감지 기능에 종속시키지 않는다.

## 9. 관리자 화면 표시

타석 카드 안에 작은 게임 상태 행을 추가한다. 두 관리자 화면은 같은 데이터·같은 신선도 계산을 쓴다.

| 확인 결과 | 표시 예 |
| --- | --- |
| Agent 신호 있고 게임 없음 | `PC 연결됨 / 골프 프로그램 미실행` |
| 실행만 확인 | `골프 프로그램 실행 / 플레이 상태 확인 불가` |
| 검증된 진행·홀 | `라운드 진행 · 3번 홀` |
| OCR 반복 확인 | `라운드 진행 · 3번 홀 (화면 인식)` |
| 메뉴 직접 확인 | `메뉴·대기` |
| 종료 이벤트 직접 확인 | `라운드 종료 확인` |
| 오래됨·충돌·가림 | `게임 상태 확인 불가` |

상세보기에는 출처, 관측시각, 마지막 수신시각, 신뢰등급, 실패 사유를 표시한다. 과거 값은 '마지막 확인: 3번 홀'처럼 별도 이력으로만 표시한다. 타석의 '이용 중' 배지는 기존 VISTA 세션만 기준으로 유지한다. PC 연결이 끊겨도 'PC 꺼짐'이나 '라운드 종료'라고 단정하지 않는다.

## 10. 신선도·충돌 규칙

- 초안: 로컬 5~10초 수집, 기존 heartbeat 주기에 최신 스냅샷 전달, 45초 이상 미관측 시 stale. 실제 주기와 TTL은 실측 후 확정한다. 필드별 관측시각으로 판단한다.
- 로그의 옛 이벤트를 다시 읽거나 PC heartbeat가 왔다고 홀의 관측시각을 지금으로 바꾸지 않는다. 장시간 같은 홀에서 유지되는 로그 방식은 유효 상태 지속을 입증할 규약이 필요하며, 없으면 TTL 뒤 unknown이다.
- 게임 재시작·PID 교체·로그 연속성 상실·코스 변경은 기존 홀/라운드를 초기화한다. 마지막 홀 또는 프로세스 종료만으로 라운드 완료를 판단하지 않는다.
- 신선한 직접 근거가 오래된 정보보다 우선한다. 같은 유효 시간에 믿을 만한 근거가 충돌하면 해당 필드 unknown/conflict, 출처를 기록한다. CPU로 동점을 결정하지 않는다.
- OCR은 초기안으로 연속 3회 일치와 홀 라벨/플레이 화면 표식 검증 후 승인한다. 점수·타수·거리 숫자를 홀로 오인하지 않도록 구분한다. 홀 건너뛰기·재시작이 가능하므로 단조 증가만 허용하지 않는다.
- 검은 화면·게임 최소화·원격 접속·보조화면 미탐지는 미실행이 아니라 캡처 불가다. UIA/로그가 살아 있으면 해당 출처만 독립적으로 사용할 수 있다.
- 서버 수신시각과 관측시각 차이가 비정상적이면 시계 오류로 낮춘다. 서버는 미래 시각을 이용해 영구 최신 상태가 되지 않게 제한한다.

## 11. 개인정보·보안·성능

- 수집 허용 목록: 프로세스 존재, 정규화된 게임 상태, 홀, 라운드 상태, 출처/진단 코드. 고객명·전화·스코어·계정·원본 창 제목·원본 로그·절대 사용자 경로는 전송하지 않는다.
- 디버그 캡처 기본 OFF. 필요 시 별도 승인된 테스트 영역만 로컬 저장, 접근 제한 및 시험 종료 시 삭제. 일반 운영에는 이미지 보관 없음.
- 게임 프로세스 권한 승격, 메모리 접근, 파일 쓰기 없이 동작하는 것을 기본 조건으로 한다. 설치·업데이트 패키지에 실제 토큰을 공개 커밋하지 않는다.
- 신규 수집기 초기 예산: 프로세스/로그 읽기 2초 제한, OCR 3초 제한, 동시 작업 1개, 초과 시 해당 감지기 중단. 재시도는 지수 지연과 상한을 둔다.
- 초기 성능 합격 목표: 추가 평균 CPU 2%p 이하(타석 PC 전체 기준), 메모리 150MB 이하, 30분 비교 시험에서 게임 프레임시간 p95 악화 5% 이하. 이는 보장값이 아니라 실측 후 승인할 예산이다.
- 인터넷 장애 중 최신 스냅샷 1개만 보관하고 복구 후 새로 관측한다. 과거 샘플을 쌓아 일괄 전송하지 않는다. 오류 로그는 제한·회전하고 비밀값을 숨긴다.

## 12. 검증 시나리오와 완료 기준

개발 테스트는 익명 fixture/모의 API 및 격리 DB를 사용한다. 운영 DB 테스트 예약·전원 제어는 별도 승인 없이 하지 않는다.

| 시험 | 합격 기준 |
| --- | --- |
| 게임 없음, 런처만, 실제 게임 실행 | 실제 게임 프로세스가 확인될 때만 running=true |
| tasklist 실패·시간초과·미설정 | null/확인 불가, 기존 세션과 화면 제어 정상 |
| 메뉴→홀1→홀2→결과→새 라운드 | 관측 근거와 일치, 이전 라운드 값 누출 없음 |
| 라운드 도중 정상/비정상 게임 종료 | 미실행과 라운드 완료를 혼동하지 않음 |
| 로그 회전·중복·부분 줄·옛 파일 | 중복/역순 샘플 차단, 연속성 상실 시 unknown |
| 상태 파일 잠김·포맷 변경 | 게임 파일 변경 없음, 감지기만 실패 |
| OCR 검은 화면·가림·다중 모니터·DPI 변경 | 잘못된 홀을 확정하지 않고 unknown |
| 장시간 같은 홀·일시정지·홀 건너뛰기 | 근거/신선도 규칙대로 표시, 임의 진행 추정 없음 |
| API 실패·잘못된 telemetry·DB 미적용·구형 Agent | 기존 heartbeat·연장·종료·자동화 회귀 없음 |
| 네트워크 단절·시계 이상·역순 응답·재시작 | stale/unknown 표시, 과거 상태 부활 없음 |
| 다른 타석 토큰·비관리자 조회 | 교차 쓰기/조회 차단, 실제 토큰 로그 없음 |
| 게임 감지기 강제 오류·중단 | 타이머·경고·잠금·기존 종료 명령 계속 동작 |

지원 버전·화면 조건에서 상태 전이 30회 이상 대조하고, 프로세스 20회 테스트 전부 일치해야 한다. 홀 감지 채택 시 최소 100개 라벨된 샘플에서 표시한 값의 정확도 99% 이상, 지원 화면에서 감지 가능 비율 95% 이상을 초기 목표로 한다. unknown을 성공 인식으로 집계하지 않는다. 8시간 관찰 시험에서 잘못된 라운드 종료 확정 0건, 신규 감지 때문에 발생한 기존 기능 장애 0건을 요구한다. 이 표본은 전체 환경의 정확도 보장이 아니다.

검증 명령은 구현 단계에서 `npm run typecheck`, 대상 lint, `npm --prefix windows-agent run check`, 단위/통합 테스트, dev 서버 중단 후 build를 수행한다. UI는 desktop/mobile에서 상태·긴 오류문구·클릭 상세를 확인한다. 한 타석의 설치본 해시/버전과 소스 일치, 감지 OFF 회귀까지 확인해야 배포 완료로 보고한다.

| 단계 | 되돌리는 방법 |

| 조사 | 설치·설정 변경 없이 종료, 승인된 임시 자료 삭제 |
| 프로세스 MVP | 감지 플래그 OFF, 기존 Agent 실행/타이머 경로 유지 |
| 로그/API 감지 | 해당 어댑터만 OFF, 프로세스 상태만 유지하고 나머지 unknown |
| 서버·DB | 서버 수집·UI 기능 플래그 OFF. 추가 nullable 컬럼은 남겨 구버전 호환 유지. 즉시 DROP 금지 |
| OCR | OCR만 OFF하고 로컬 워커 종료, 다른 감지와 Agent 유지 |
| 타석 배포 | 이전 검증 패키지로 복구하되 로컬 인증·타석 설정 보존, Agent 중복 실행 방지 |

롤백 후 서버에 남은 게임 스냅샷은 표시하지 않거나 stale로 처리한다. 표시를 지우기 위해 예약/세션 데이터를 삭제하지 않는다. DB 제거는 모든 구버전·신버전 의존 확인 후 별도 승인된 작업이다.

## 14. 위험·미확정 사항·MVP 구분

| 위험/미확정 | 대응 |
| --- | --- |
| 제품명·버전·실행파일 미확정 | 현장 속성과 프로세스 확인. 파일명으로 제조사 추정 금지 |
| Logs가 장애 기록만 제공 | 상태 감지 부적합 판정, 창/UIA 조사로 이동 |
| 저장된 홀 값이 이전 라운드 값 | 이벤트 시각·프로세스 생명주기 검증, 불가하면 unknown |
| 업데이트로 형식 변경 | 검증된 버전 프로필만 활성화, 미지원 버전은 프로세스만 표시 |
| 게임이 접근성/캡처를 제공하지 않음 | 공식 지원 요청 또는 unknown 범위 수용. 우회 변조하지 않음 |
| 여러 게임/라운드 동시 실행 | 임의로 하나 선택하지 않음. 대상 창/프로세스 정책 현장 확인 필요 |
| 모니터·TV·프로젝터 복제/확장 차이 | 실제 렌더링 화면 기준으로 선택, 전원 상태와 혼동 금지 |
| Agent 본체/감지기 오류 전파 | 워커 격리, 제한 시간, 기능 플래그, 기존 흐름 회귀 |

MVP 필수: 정확한 프로세스 삼상값, 관찰 전용 구조, 선택적 telemetry, stale/unknown, 출처/시각 상세, 두 관리자 화면 일치, 기존 기능 무영향.

MVP 조건부: 실증된 공식 API/로그가 있을 때만 메뉴·홀·라운드 종료 추가. 없으면 해당 필드가 확인 불가인 MVP로 승인받는다. OCR은 필수가 아니며 증거 없이 일정에 포함하지 않는다.

향후: 제품별 어댑터, OCR 보조, 상태 전이 이력·통계, 감지 품질 감시. 플레이 상태에 따른 자동 연장·과금·강제 종료, 스윙 감지, 스코어 수집은 이번 범위 밖이며 별도 제품·안전 검토가 필요하다.

## 15. 이번 문서 작업의 검증 기록

- preflight 실행 시도 및 권한 제약 확인, 공용 원장 전체와 git 상태 확인.
- Electron/legacy Agent, heartbeat/session API, Agent 저장 함수, 타석 조회 및 마이그레이션 정의를 읽고 분석.
- 첨부 사진은 설치폴더 증거로만 사용. 현장 파일/게임/운영 DB는 직접 조사하지 않음.
- 변경 범위는 이 계획서와 공용 원장뿐. 구현·빌드·테스트 실행·커밋·푸시·배포·기기 조작 없음.
- 다음 작업은 현장 조사이며, 자료 확인 전 감지 방식과 홀 감지 가능 여부는 미확정.

## 16. 구현 현황

2026-09-12 현장 재현 결과를 반영해 Agent 0.6.0 구조로 개편했다. 실제 실행파일은 `ScreenGolf.exe`이며 프로세스 감지는 시흥점 기본 설정에서 켜진다. 공개 기본 설정과 비밀 로컬 설정은 대체가 아니라 병합되어, 기존 로컬 설정에 새 항목이 없어도 감지 기능이 꺼지지 않는다.

실시간으로 읽을 수 있는 `ScreenGolf\Saved\Logs\ScreenGolf.log`에서 로비 모드와 코스/게임 모드 전환을 상태 머신으로 구현했다. 따라서 프로그램 미실행, 메뉴·대기, 라운드 진행을 구분할 수 있다. 라운드에서 로비로 돌아온 경우에는 완료와 중도 종료를 구분할 직접 근거가 없어 `확인 불가`로 유지한다.

홀 번호와 마지막 홀 종료 신호가 있는 `ScreenGolf\Binaries\Win64\Logs\main_*.log`는 게임 실행 중 잠겨 있으므로 실시간 상태에 사용하지 않는다. 파일이 열린 뒤에는 `02hole` 같은 홀 후보와 `IsEndedHole ... State: 1` 종료 후보를 로컬 진단에만 남긴다. 원문 로그와 파일 경로는 보관·전송하지 않으며, 후보는 현재 상태로 승격되지 않는다. 결과 파일은 `%APPDATA%\vista-windows-agent\logs\game-monitor-diagnostics.log`이다.
