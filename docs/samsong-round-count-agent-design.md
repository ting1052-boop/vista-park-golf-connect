## 0. 한 줄 요약

타석 PC의 Agent가 **게임 로그를 원장처럼 읽어** 라운드마다 "언제 코스에 들어갔고, 어느 홀들을 끝냈는가"라는 사실만 서버에 보고하고,
**"9홀 이상 끝낸 판 = 1회"** 판정과 일별 집계는 서버가 한다. 예약·세션·고객 화면은 쓰지도 바꾸지도 않는다(시흥은 기존 흐름을 그대로 둔 채 집계만 더한다).

1단계에서 화면에 나오는 숫자는 두 종류다.

- **오늘 시작 N회** — 일반 코스 진입 수. 다음 heartbeat에 실려 거의 실시간이지만 **잠정**이다. 게임 수가 아니다
- **어제 확정 게임 N회** — 게임이 끝나고 홀 기록을 읽어 9홀 이상으로 확인된 판 수. 다음 날 아침(또는 게임 프로그램 종료 뒤) 확정된다

가장 중요한 제약: **몇 홀을 끝냈는지 알 근거는 아직 현장에서 검증되지 않았다.** 구현은 0단계(현장 증거 수집) 관문을 통과한 뒤에만 홀 판정 코드를 쓴다.

**가장 큰 남은 위험: 9홀 이상 한 판이 두 번 세어지는 것.** 정상 18홀 한 판이 로그에 두 코스 구간이나 1~9홀 두 묶음으로 남으면 1회가 2회가 된다. 현장 로그로 반드시 확인한다(§2 모름 7, §5.4, 테스트 7c). `오늘 시작`도 같은 이유로 한 판을 2로 셀 수 있다.

## 1. 목표와 정의

### 1.1 용어

| 항목 | 정의 |
| --- | --- |
| 게임 시작 | 일반 코스(연습·튜토리얼·테스트 제외) 진입 1건. 진입을 읽으면 다음 heartbeat에 보고한다. **잠정값이며 게임 수가 아니다** (합의 2026-11-21) |
| 1회 (확정 게임) | 일반 코스에서 **서로 다른 홀 9개 이상의 "홀 종료"가 확인된** 플레이 1건 (사용자 확정 2026-11-17). 18홀을 다 쳐도 1회, 9홀만 쳐도 1회 |
| 중도 종료 | 홀에 1개 이상 들어갔지만 홀 종료가 0~8개인 플레이(첫 홀도 못 끝내고 나간 판 포함). 기록은 남기되 0회 |
| 연습 이용 | 연습장 맵(`Practice_`)에 머문 구간. **게임 수·시작 수에 넣지 않고** 건수와 시간만 따로 보여준다 (따로 표시는 합의 2026-11-21, 1분 미만 버림은 기본값) |
| 확인 대기 | 라운드가 있었지만 홀 근거를 아직 못 읽었거나, 읽었지만 짝짓기·해석에 실패한 상태. **집계에 넣지 않고 따로 보여준다** |
| 하루 | 한국 시간. **시작 수는 코스 진입 날짜**, 확정 게임·중도 종료·확인 대기는 **라운드가 끝난 날짜** |
| 세지 않는 것 | 튜토리얼·테스트 맵(`Tutorial_`, `Test_`), Agent 설치 이전의 과거 기록 |

현장 규모: 시흥 타석 3대(A-01~A-03), 삼송 타석 PC 8대·밤에 끈다. 손님은 보통 18홀을 다 친다.

### 1.2 과금 원칙 (합의 2026-11-21)

**Agent 집계는 통계와 정산 대조용이다. 과금 근거가 아니다.**

| 과금 방식 | 과금 근거 | Agent 숫자의 역할 |
| --- | --- | --- |
| 시간제 | 예약·입장 세션(`access_sessions` 등 기존 흐름) | 대조만 |
| 게임당 | 키오스크·POS·관리자가 확정한 기록 | 누락·무단 이용·운영 상태 확인 |

- Agent는 과금 정책을 모른다. Agent 설정에 요금·과금 방식 값을 넣지 않는다
- 시간제·게임당 과금 설정은 **실제 결제 기능을 만들 때** 그 기능 쪽에 추가한다. 이 지시서 범위가 아니다
- 화면에서 Agent 숫자 옆에 금액을 계산해 보여주지 않는다

### 1.3 1단계 범위와 범위 밖

1단계(이 지시서): 게임 시작 실시간 잠정 집계, 게임 종료 후 로그 분석으로 확정(9홀 이상 = 1회 / 1~8홀 = 중도 종료 / 연습 = 연습 이용 / 근거 부족·실패 = 확인 대기), 다음 날 또는 게임 프로그램 종료 뒤 확정, 대시보드 5개 지표(§8).

1단계에서 **하지 않는다**: 현재 몇 번 홀인지, 끝날 예상 시각(ETA) — 2단계(§15). 사람 수(`4명 플레이` 등) — Agent가 알 수 없다. 매장이 예약에서 인원을 받으면 예약 데이터로만 보여준다(이 지시서 범위 밖).

그 밖의 범위 밖: 예약·결제·이용시간 제한, 고객 화면(경고·잠금), 전원 자동화(WOL·스케줄), 회원 식별, 송도 동작 변경, 시흥의 기존 세션·키오스크·예약·종료 동작 변경.

### 모름 (0단계에서 확인해야 구현할 수 있다)

1. 삼송 PC의 프로그램이 시흥과 **같은 제품·같은 로그 형식**인가
2. `main_*.log`가 "끝난 뒤"란 **프로그램 종료 뒤**인가, 라운드 종료 뒤인가 (확정 시점이 달라진다)
3. `main_*.log` 줄에 **시각이 있는가**, 홀을 끝낼 때마다 홀 종료 줄이 **빠짐없이** 남는가 (9개를 세야 하므로 한두 개 빠지는 것도 문제다)
4. `main_*.log`와 `ScreenGolf-backup-*.log`가 디스크에 **며칠치** 남는가
5. 로그 시각이 UTC인가 현지 시각인가
6. 한 번 코스에 들어간 채 **다시하기로 2판**을 칠 수 있는가 (로비 복귀 없이). 그렇다면 `시작`은 1, 확정은 2가 될 수 있다
7. **정상 18홀 한 판이 코스 구간 1개, 홀 번호 1~18로 남는가.** 9홀 기준에서는 이것이 가장 위험하다. 한 판이 9홀 코스 맵 두 개(A코스 → B코스)로 로드되거나, 홀 번호가 10번이 아니라 1번부터 다시 시작하면 18홀 한 판이 **2회로 세어진다**(시작 수도 2). 시흥 A-02 실측(코스 진입 1회에 2~18홀)으로는 괜찮아 보이지만 삼송은 미확인이다
8. **시흥 A-02의 60분 세션.** 대시보드 스크린샷에 `21:55~22:55` "Agent 사용 신호 기준" 60분 세션이 보였다. 시험하던 시각에 생긴 것은 맞지만, 이것이 **시흥의 운영 정책(사용 신호로 60분 세션을 만드는 것)인지는 확인되지 않았다.** 운영 데이터(해당 시각의 세션 생성 경로·예약 유무)로 확인하기 전에는 시흥 설정의 `usageMonitoringEnabled` 등 이용 감지 값을 바꾸지 않는다. 집계 기능은 이 세션과 무관하게 동작해야 한다(D6)

### 구현 전에 알아야 할 저장소 상태

- **운영 DB가 바뀌었다.** 운영 사이트는 Supabase `bgguqxmhmnuujdkbeewz`를 쓴다. 이 저장소의 `.env.local`과 여러 문서는 예전 프로젝트를 가리키며 그 주소는 더 이상 없다. `.env.local`로 운영을 조회·수정하려 하지 말 것. migration은 사용자가 현재 운영 프로젝트의 SQL Editor에서 실행한다.
- **Supabase 전송량 초과 사고가 있었다**(2026-11, `traffic-audit-20261106.md`). 새 PC가 15초 주기 구형 통신을 쓰면 안 된다(§9).
- **Agent 소스가 두 갈래다(2026-11-20 확인).** ① 이 작업 폴더(main): `windows-agent/electron-main.js` 등에 다른 작업자의 미커밋 **0.9.9**(observer 통신). ② Codex worktree `C:\Users\ting\.codex\worktrees\7394\Vista_m`: 커밋 `2b1af58`(main에 없는 갈래 커밋, "Agent 재시작 후 진행 중 ScreenGolf 상태 복원")과 그 위의 미커밋 **0.9.15**(송도 최종 후보, 화면 카운터 제거·golf-usage-monitor·renderer 변경, 로컬 빌드만, **미배포**). 서로를 포함하지 않는다. 어느 쪽도 되돌리거나 덮어쓰지 않는다. 로그 신호 정의(`screen-golf-monitor.js`의 정규식·`parseScreenGolfEvents`, `game-log-probe.js`, `game-log-locator.js`)는 두 갈래가 같다(줄바꿈 차이만). `screen-golf-monitor.js`의 `observe` 되살리기 동작만 다르다.

| # | 결정 | 이유 |

| D1 | **Agent는 사실만 보고하고, "1회" 판정은 서버가 한다** | 판정 규칙(예: 9홀 처리)이 바뀌어도 PC를 다시 설치하지 않고 과거 데이터까지 다시 계산할 수 있다 |

| D5 | 근거가 없으면 **"확인 대기"로 두고 세지 않는다.** 시간 길이로 추정해서 세지 않는다 | 로비 복귀만으로 세면 한두 홀 치고 나간 판까지 들어가 숫자가 부풀고, 틀렸는지 알 방법이 없다 |

| D7 | 라운드 분석은 **매장 설정**(`stores.agent_round_counting`)과 등록 PC 유형(`bay_pc_registry.pc_type = 'park'`)이 모두 맞을 때만 켠다. 시흥·삼송 ID·코드를 코드에 박지 않는다 | 한 매장에 골프연습장과 파크골프가 섞일 수 있다 |
| D8 | **`게임 시작`은 잠정값으로만 쓰고, 확정 게임 수와 섞지 않는다** (합의 2026-11-21) | 진입만으로는 1홀 치고 나간 판과 18홀 판을 구분할 수 없다. 실시간 필요는 "지금 돌고 있나"이고, 그건 시작 수로 충분하다 |
| D9 | **Agent는 과금을 모른다.** 요금·과금 방식 설정을 Agent에 두지 않는다(§1.2) | 과금 근거는 세션·키오스크·POS다. Agent 숫자가 돈을 결정하면 로그 하나 빠질 때 분쟁이 된다 |

D4의 결과로 **확정 숫자는 늦게** 나온다. `main_*.log`가 프로그램이 꺼져야 열린다면, 밤에 PC를 끄는 삼송에서는 **다음 날 아침 부팅 때 전날 숫자가 확정**된다. 사용자가 이 지연을 허용했다(2026-11-17, 2026-11-21 재확인). 그동안 당일 상황은 `오늘 시작`으로 본다. 0단계 결과에 따라 더 빨라질 수 있다(§5 관문). 시흥 PC가 밤에 게임을 끄지 않거나 꺼지지 않으면 그동안 "확인 대기"로 남는다. 시흥의 야간 종료·자동 실행 여부는 0단계 안내문으로 확인한다.

## 5. 0단계 — 현장 증거 수집 (필수 관문)

홀 판정 코드(§6.4)는 이 단계의 결과 파일 없이는 작성하지 않는다. §6.1~6.3(시작 보고 포함), §7, §8은 0단계와 무관하게 먼저 만들 수 있다.

### 5.1 만들 것: 읽기 전용 수집기 (작성 완료, 2026-11-20)

- `windows-agent/tools/collect-round-evidence.ps1` + 같은 폴더의 `.bat` 실행기
- **PowerShell 5.1 규칙(이 저장소에서 실제로 사고가 났던 것들)**
  - 한글이 들어간 `.ps1`은 UTF-8 **BOM** 필수. BOM이 없으면 조용히 오동작한다
  - `.bat`은 ASCII + CRLF, 영문 이름의 `.ps1`만 호출
  - 검증은 반드시 `powershell -File`로 **파일째 실행**한다. 명령을 떼어 실행한 것은 검증이 아니다
- 게임·Agent의 파일을 수정·삭제하지 않는다. 잠긴 파일을 우회해 열지 않는다(VSS·권한 상승·프로세스 접근 금지). 관리자 권한을 요구하지 않는다

### 5.2 수집 내용

| 대상 | 기록할 것 |
| --- | --- |
| 환경 | PC 이름, 화면 해상도, `C:\PARK_*-VISTA` 후보 폴더, `ScreenGolf.exe`의 파일 버전·크기·수정시각, 지금 실행 중인지 |
| 로그 파일 목록 | `Saved\Logs`와 `Binaries\Win64\Logs`의 파일별 이름 유형·크기·만든 시각·수정 시각 (보존 기간 판단용) |
| 열림 여부 | 각 `main_*.log`를 읽기 공유로 열어본 결과(성공/오류 코드). 게임 실행 중 1회, 종료 후 1회 실행해 비교 |
| `ScreenGolf*.log` | 코스 진입·로비·게임모드·종료 요청 줄의 **시각 + 종류 + 코스 ID**만 |

| 시각 기준 | 각 로그의 마지막 줄 시각과 파일 수정 시각(UTC) — 로그가 UTC인지 판단용 |

"줄 모양"은 원문이 아니다. 숫자는 `#`, 따옴표 안은 `""`, 한글 등 비ASCII는 `?`로 바꾼 것이다. 고객 이름·계정이 결과에 들어가지 않게 하기 위해서다. 원문 줄은 저장하지 않는다.

- 범위 제한: 최근 14일, 파일 20개, 결과 5MB 이하
- 결과: 수집기 폴더에 `round-evidence-<PC이름>.jsonl` 하나(실행마다 한 줄 추가, 게임 켠 채 1회 + 완전 종료 후 1회가 한 파일). 화면에는 요약만 출력
- 줄 모양은 위 규칙에 더해 **허용 단어 외 영문 단어를 `w`로** 바꾼다(ASCII 이름·계정 차단). 출력에 비ASCII가 있으면 `?`로 바꾼다
- 구현: `windows-agent/tools/collect-round-evidence.ps1`·`.bat`, 자체 검사 `collect-round-evidence.selftest.ps1`, 현장 안내문 `README-round-evidence-ko.txt`
- 사용자가 USB로 가져오면 `windows-agent/fixtures/round-evidence/`에 둔다. 커밋 전에 개인정보가 없는지 사람이 한 번 본다

## 6. Agent 설계 (버전 0.10.0, 같은 EXE)

새 동작은 서버가 `pc_type = park`인 PC에만 내려주는 설정 `roundCountingEnabled: true`일 때만 켜진다. `range` PC는 기존 60분 이용 감지만 유지한다. 이 값이 없는 타석의 동작은 한 줄도 달라지면 안 되고, 이 값이 켜진 시흥 타석도 세션·고객 화면·종료 동작은 그대로다(D6).

### 6.1 라운드 원장 `round-ledger.js` (신규, Electron 없이 테스트 가능해야 한다)

기존 `screen-golf-monitor.js`는 **실시간 화면 상태용**이며 "시작할 때 과거 로그는 무시"한다. 집계는 요구가 반대(빠짐없이)이므로 **별도 모듈**로 만든다. 줄 해석(`parseScreenGolfEvents`, `parseLogTimestamp`, `classifyCourse`)은 기존 것을 재사용한다.

- **체크포인트 읽기**: 실행 단위(게임을 한 번 켠 로그 파일)마다 "어디까지 읽었는지"를 디스크에 남기고 이어 읽는다. 파일이 새로 만들어졌으면(크기가 줄었거나 첫 시각 줄이 달라짐) 직전 실행의 백업 파일(`ScreenGolf-backup-*.log`) 나머지를 먼저 처리한다. 백업 파일 이름 규칙은 0단계 결과로 확정한다
- 실행 중에는 **기존 게임 감시 주기**에 맞춰 새 줄을 읽는다(코스 진입을 늦어도 다음 heartbeat에 실을 수 있게). 새 타이머를 따로 만들지 않는다
- **실행 키** `launchKey`: 그 로그 파일의 첫 시각 줄의 시각 문자열
- **라운드 구간**: 일반 코스 진입부터 아래 중 하나까지

| 종료 종류 `endKind` | 조건 |
| --- | --- |
| `returned_to_lobby` | 로비 진입 줄 |
| `course_changed` | 진행 중 다른 코스 진입 줄 |
| `game_exit` | 종료 요청 줄 |
| `log_ended` | 로그가 거기서 끝나고 다음 실행이 시작됨(전원 차단·강제 종료). 다음 부팅 때 확정된다 |

- **종료 종류로 게임 여부를 판단하지 않는다.** 9홀 이상 끝내고 그냥 자리를 떠나 PC가 꺼져도 1회다. 판단은 홀 사실만으로 한다
- **연습 구간**: 연습장 맵(`classifyCourse`가 `practice`) 진입부터 위 종료 조건 중 하나까지. **1분 미만은 버린다**(잘못 누르고 나온 것). 라운드와 같은 방식으로 ID를 만들고 **닫힌 뒤에만** `kind: "practice"`로 보고한다(시작 보고 없음). 홀 대조는 하지 않는다. 튜토리얼·테스트 맵은 기록하지 않는다
- **결정적 라운드 ID**: `sha256(agentId | launchKey | 코스진입 시각 문자열 | courseId)`의 앞 32자리 16진수를 UUID 모양으로 만든다. 서버 검증식(`버전 자리 1~8, 변형 자리 8·9·a·b`)을 통과하도록 버전 자리는 `5`, 변형 자리는 `8`로 고정한다. 진입 시점에 이미 계산되므로 시작 보고와 확정 보고가 같은 ID를 쓴다
- **설치 시점 경계**: Agent가 이 기능으로 처음 실행된 시각을 저장하고, 그 이전에 시작된 라운드는 보고하지 않는다
- **절대 시각**: 로그 시각은 UTC인지 현지 시각인지 0단계에서 확정한다. 변환 보정값은 "파일 수정 시각 − 마지막 줄 시각"을 30분 단위로 반올림해 구한다. 구하지 못하면 관측 시각을 쓰고 `timeBasis: "observed"`로 표시한다. 추정한 시각을 로그 시각인 것처럼 보내지 않는다
- 원장 파일은 임시 파일에 쓰고 이름을 바꾸는 방식으로 저장한다(기존 `usage-window-monitor.js`의 `persist`와 같은 방식). 파일이 깨졌으면 집계를 멈추고 진단만 남긴다. heartbeat와 종료 명령은 계속 동작해야 한다

### 6.2 보고와 개정 번호

| 개정 `revision` | 언제 | 상태 `status` | 홀 근거 `holeSource` |
| --- | --- | --- | --- |
| 1 | 일반 코스 진입 줄을 읽었을 때 (`게임 시작`) | `open` | `none` |
| 2 | 라운드 구간이 닫혔을 때 | `closed` | `none` |
| 3 | `main_*.log` 대조가 끝났을 때 | `closed` | `native_log` |

- 연습은 닫힐 때 개정 2 하나만 보낸다
- Agent가 꺼져 있다가 따라잡은 라운드는 개정 1을 건너뛰고 2(또는 3)부터 보낸다. 서버는 개정 1이 없어도 된다
- 같은 라운드의 보고는 outbox에 **최신 개정 하나만** 남긴다. 서버 확인(ACK)을 받은 것만 지운다. 영구 거절은 로컬 거절 목록(최대 100건)으로 옮긴다. 기존 `round-event-outbox.js`의 방식을 따른다
- 개정 1은 heartbeat 하나에 실려 가는 작은 보고다. **즉시 전송용 별도 트리거를 만들지 않는다.** 다음 heartbeat에 실린다(삼송 같은 관찰 매장은 60초, 시흥은 기존 세션 heartbeat 주기)

### 6.3 통신

- `roundReports`를 **기존 heartbeat 본문에** 실어 보낸다(한 번에 최대 10건). 새 엔드포인트를 만들지 않는다
- **60초 observer 통신을 쓴다.** 지금은 Agent(`observer-transport.js`)와 서버(`agent-observer-protocol.ts`) 양쪽에 송도 매장 ID가 박혀 있다. Agent 쪽 조건을 `monitorOnly === true && (송도 ID || observerTransport === true)`로 넓힌다. 송도 조건은 그대로 둔다
- `traffic-audit-20261106.md`가 지적한 observer 결함 두 가지를 **출시 전에 고친다**: ① 이른 이벤트 전송이 실패했을 때 `retryAt`보다 `nextAt`이 늦으면 재시도가 정상 주기까지 밀리는 문제 ② 세션 조회만 실패할 때 백오프가 걸리지 않는 문제. 가짜 시계 회귀 테스트를 추가한다
- observer 협상이 실패하면 기존 방식으로 돌아가되 **집계 보고는 계속 간다**
- **시흥**(`monitorOnly` 아님)은 지금의 세션 통신을 그대로 쓰고 `roundReports`만 기존 heartbeat에 싣는다. observer 일반화와 위 결함 수정은 삼송(monitorOnly) 확장 전까지 끝낸다

### 6.4 홀 사실 `native-hole-log.js` (0단계 G1 통과 후에만 작성)

- 패턴은 `fixtures/round-evidence/`의 실제 줄 모양으로만 만든다. `game-log-probe.js`의 후보 정규식을 그대로 승격하지 않는다
- 파일별 체크포인트(경로 해시·크기·수정 시각·처리 완료 여부). 다시 처리해도 같은 결과가 나와야 한다
- 열기에 실패하면(잠김) 건너뛰고 다음 기회에 다시 본다. 우회하지 않는다
- **대조 시점**: Agent 시작 시 / 게임 프로세스가 꺼진 것을 본 직후 / 실행 중에는 10분마다 열기만 시도. 0단계에서 실행 중에도 읽힌다고 확인되면 60초로 줄인다
- **한 판의 단위는 "홀 진행 묶음(run)"** 이다. 라운드 구간 안에서 이미 들어갔던 홀에 다시 들어가면 새 묶음을 시작한다(다시하기 대응). 묶음마다 18비트 두 개를 만든다: `enteredMask`(들어간 홀), `endedMask`(끝낸 홀). 1번 홀이 가장 낮은 비트
- **라운드와 짝짓기**
  - 시각이 있으면: 홀 줄의 시각이 라운드 구간 `[시작, 끝 + 120초]`에 드는 것을 그 라운드에 붙인다
  - 시각이 없으면: 같은 실행 단위 안에서 **순서로** 짝짓는다(k번째 일반 코스 구간 ↔ k번째 코스 로드 구간). 개수가 맞지 않으면 그 실행의 라운드를 **전부 `none`으로 두고** 진단을 남긴다. 추측으로 맞추지 않는다
- 원문 줄·파일 경로·고객 식별 정보는 저장하지도 보내지도 않는다

### 6.5 설정 — 3구분만 (합의 2026-11-21)

EXE는 하나다. 매장·타석마다 켜는 기능을 **세 가지로만** 구분한다. 과금 설정은 두지 않는다(D9).

| 구분 | 하는 일 | 설정 키 | 적용 |
| --- | --- | --- | --- |
| 기본 가동 감시 | heartbeat, 게임 실행 여부, 종료 명령 | 기존 기본값 | 전 매장 |
| 60분 이용 감지 | 사용 신호로 60분 이용 구간 기록(`usage-window-monitor.js`, `agent_usage_events`) | 기존 `usageMonitoringEnabled` | 송도(현행). 시흥은 §2 모름 8 확인 전 **현 설정 유지** |
| 파크골프 라운드 분석 | 이 지시서 | 새 `roundCountingEnabled` | 라운드 분석 매장의 `park` PC만 |

세 구분은 **독립된 기존·신규 설정 키**다. "프로필" 같은 새 열거형이나 설정 화면을 만들지 않는다. 관리 화면·설치 안내에서 이 세 이름으로 부르기만 한다.

삼송(관찰 전용 매장) 설치 설정:

```json
{ "monitorOnly": true, "roundCountingEnabled": true, "observerTransport": true,
  "gameMonitoringEnabled": true, "gameProcessNames": ["ScreenGolf.exe"],
  "gameLogDiagnosticsEnabled": false, "usageMonitoringEnabled": false }
```

**시흥의 `park` PC는 기존 설치 설정에 `roundCountingEnabled: true` 하나만 더한다.** `range` PC에는 넣지 않는다. `monitorOnly`·`observerTransport`·`usageMonitoringEnabled: false`를 시흥에 넣으면 세션 흐름이 깨진다.

`roundCountingEnabled`는 `electron-main.js`의 `loadConfig`에서 `=== true`로만 켠다. `monitorOnly`가 아닌 타석에서 이 값이 켜져도 고객 화면·세션 종료 동작은 기존 `resolveBayPolicy`가 그대로 정한다.

### 6.6 화면 OCR 경로 (이번에 구현하지 않는다)

§15의 2단계 순서에서 **마지막**이다. 들어간 홀만 알 수 있어 "18번 홀 진입"까지만 증명되고, PC마다 `calibrate-hole-roi.ps1` 보정과 2초마다 OCR 실행이 필요하다. 서버 스키마에는 `holeSource: "ocr"` 자리를 미리 두되, 판정 규칙은 별도 승인 후 정한다.

## 7. 서버 설계

### 7.1 migration 하나 (`supabase/migrations/2026MMDD0001_agent_rounds.sql`, `schema.sql`에도 같은 내용)

```sql
alter table public.stores
  add column if not exists agent_round_counting boolean not null default false;

create table if not exists public.agent_rounds (
  agent_device_id uuid not null references public.agent_devices(id) on delete cascade,
  round_id uuid not null,
  store_id uuid not null references public.stores(id) on delete cascade,
  bay_id uuid not null references public.bays(id) on delete cascade,
  revision integer not null check (revision >= 1),
  status text not null check (status in ('open', 'closed')),
  course_id text,
  started_at timestamptz not null,
  ended_at timestamptz,                               -- open 이면 null
  time_basis text not null check (time_basis in ('log', 'observed')),
  end_kind text check (end_kind in ('returned_to_lobby', 'course_changed', 'game_exit', 'log_ended')),
  hole_source text not null check (hole_source in ('none', 'native_log', 'ocr')),
  kind text not null default 'course' check (kind in ('course', 'practice')),
  hole_runs jsonb not null default '[]'::jsonb,       -- [{ "enteredMask": int, "endedMask": int }]
  counted_games smallint not null default 0 check (counted_games between 0 and 6),
  completion text not null check (completion in ('open', 'counted', 'partial', 'unverified', 'practice')),
  start_date date not null,                           -- started_at 의 한국 날짜. 서버가 계산 (시작 수)
  play_date date,                                     -- ended_at 의 한국 날짜. 서버가 계산 (확정 수). open 이면 null
  agent_version text not null,
  received_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (agent_device_id, round_id),
  check ((status = 'open'   and ended_at is null     and end_kind is null     and play_date is null and kind = 'course')
      or (status = 'closed' and ended_at is not null and end_kind is not null and play_date is not null)),

create index if not exists agent_rounds_store_start_idx on public.agent_rounds (store_id, start_date);

```

같은 파일에 함수 두 개(둘 다 `security definer`, `service_role`에만 실행 권한. 기존 `store_agent_game_telemetry_if_newer`와 같은 방식):

- `upsert_agent_round(...)` — 없으면 넣고, 있으면 **들어온 개정이 더 높을 때만** 바꾼다. `closed`를 `open`으로, `native_log`를 `none`으로 낮추지 않는다. 반환값으로 `stored` / `already_current`를 구분한다
- `agent_round_daily_counts(p_store_id uuid, p_from date, p_to date)` — 날짜·타석별로 돌려준다:
  - `started` — `kind = 'course'` 행 수, **`start_date` 기준** (open·closed 모두)
  - `counted_games` 합, `partial` 건수, `unverified` 건수 — **`play_date` 기준**
  - `open_stale` — 시작 후 12시간이 지났는데 아직 `open`인 행 수, `start_date` 기준 (화면에서 확인 대기에 더한다)
  - `practice` 건수·분 합 — `play_date` 기준
  - 기간은 최대 92일. **행을 내려받아 세지 않고 DB에서 합산**한다(전송량 절약, 기존 "하루 100건 상한" 문제 제거)
- `agent_round_pending(p_store_id uuid)` — 타석별 `(bay_id, 확인 대기 건수, 가장 오래된 대기 날짜)`. 확인 대기 = 최근 31일 안의 `unverified` + 시작 후 12시간 지난 `open`. **어제·오늘로 자르지 않는다**(며칠 묵은 대기가 카드에서 사라지지 않게)

**긴 라운드**: 길이 상한은 7일이다(12시간이 아니다). 시흥처럼 게임을 밤새 켜 두면 손님이 18홀을 끝내고 로비로 가지 않은 판이 다음 코스 진입·종료 때까지 열려 있을 수 있다. 이런 닫힘도 그대로 저장하고 판정은 홀 사실로만 한다(D5와 같은 원칙). 그래서 그런 판의 확정 날짜(`play_date`)는 닫힌 날로 늦게 잡힐 수 있다. 7일을 넘는 닫힘은 거절되고 행은 `open`으로 남아 31일 동안 확인 대기에 보인다.

배포 순서: **migration 먼저, 코드 나중.** 코드는 migration이 없어도 기존 기능이 죽지 않아야 한다(§7.2의 조회 실패 처리).

### 7.2 heartbeat 계약 추가 (`src/app/api/agent/heartbeat/route.ts`)

요청 본문에 선택 필드 `roundReports` 추가:

```json
{ "roundId": "uuid", "revision": 3, "status": "closed", "kind": "course", "courseId": "…",
  "startedAt": "ISO", "endedAt": "ISO", "timeBasis": "log", "endKind": "returned_to_lobby",
  "holeSource": "native_log", "runs": [{ "enteredMask": 262143, "endedMask": 262143 }], "agentVersion": "0.10.0" }
```

개정 1(`status: "open"`)은 `endedAt`·`endKind`를 빼고 `runs: []`, `holeSource: "none"`으로 보낸다.

응답에 `roundReportAcks: [{roundId, revision}]`, `roundReportRejected: [{roundId, revision, code}]`, `roundReportRetryable` 추가.

- 검증·저장은 새 파일 `src/lib/agent-round-reports.ts`에 둔다. 기존 `agent-round-events.ts`는 수정하지 않는다
- 검증: UUID 형식, 개정 1 이상, `status`와 `endedAt`·`endKind` 유무 일치, `open`은 `kind: course`만, `kind`는 `course`/`practice`(`practice`면 `closed`, `holeSource: none`, `runs: []`, 길이 1분 이상), 마스크 0~262143, 묶음 6개 이하, 끝 ≥ 시작, 길이 7일 이하, 31일보다 오래되지 않음, 미래 5분 이내, 문자열 길이 상한, 한 번에 10건 이하
- **프로필 확인**: `roundReports`가 왔을 때만 `stores.agent_round_counting`과 토큰 타석의 `bay_pc_registry.pc_type`을 조회한다. 매장 기능이 꺼져 있거나 `park`가 아니면 `profile_disabled`로 영구 거절. 조회가 실패하면(열 없음 포함) `storage_unavailable`로 재시도시킨다. **`getAgentByToken`의 조회 열은 바꾸지 않는다**
- 매장·타석은 요청 본문이 아니라 **토큰으로 정해진 값**만 쓴다(기존 원칙)
- 이미 같거나 더 높은 개정이 있으면 ACK한다(재전송에 안전)
- 저장 실패가 heartbeat 자체나 종료 명령 전달을 막으면 안 된다(기존 `roundEvents`·`usageEvents` 처리와 같은 격리, 같은 위치에 블록 하나 추가)

### 7.3 판정 (`src/lib/round-classify.ts`, 순수 함수 + 테스트)

```
MIN_HOLES_FOR_GAME = 9   (사용자 확정 2026-11-17)

status = open            → completion = open,       countedGames = 0   (시작 수에만 들어감)
kind = practice          → completion = practice,   countedGames = 0
holeSource = none        → completion = unverified, countedGames = 0
holeSource = native_log  → countedGames = endedMask 의 켜진 비트가 9개 이상인 묶음의 수
                           completion = countedGames > 0 ? counted : partial
holeSource = ocr         → 이번 범위에서는 unverified 로 취급 (§6.6)
```

- 18홀을 다 끝낸 묶음도 **1회**다(2회가 아니다). 한 묶음은 최대 1회
- 다시하기로 같은 구간에 9홀 이상 묶음이 2개면 2회
- 9홀 미만 묶음 두 개를 합쳐 1회로 만들지 않는다
- `native_log`인데 묶음이 0개(홀 줄을 하나도 못 짝지음)면 `unverified`로 둔다. 묶음이 있으면(홀에 들어감) 끝낸 홀이 0개여도 `partial`이다(§1.1 중도 종료 0~8)

`9`는 이름 붙은 상수 하나로 둔다. 매장별 설정 열은 만들지 않는다(요구가 생기면 그때). 규칙이 바뀌면 `hole_runs`로 과거 행을 다시 계산할 수 있다.

### 7.4 설치 설정과 릴리스

- `src/lib/agent-bay-config.ts`는 `pcType`과 매장 설정을 함께 받아 `park`일 때만 §6.5의 값을 넣는다(관찰 전용 매장은 전체 값, 시흥처럼 세션 매장은 `roundCountingEnabled`만). `range`는 기존 `golf_input` 60분 감지만 유지한다. 송도(`VISTA-XII`) 분기는 그대로 둔다
- `src/lib/agent-release.ts`: 릴리스 포인터가 지금 전 매장 공용 하나다. **집계 매장용 포인터를 따로** 둔다(예: `AGENT_RELEASES = { default: 0.9.8, roundCounting: 0.10.0 }`). 기존 값을 0.10.0으로 바꾸면 송도·시흥 재설치가 검증 안 된 버전을 받게 된다
- `src/lib/agent-observer-protocol.ts`: 송도 ID 조건에 "집계 매장" 조건을 **추가**한다. 판단에 필요한 매장 값은 observer 헤더가 온 요청에서만 조회한다

어제 판이 오늘 이후에 늦게 확정되면(PC를 하루 안 켬, 시흥에서 게임을 계속 켜 둠) 그 숫자는 `어제 확정`이 아니라 **일별 표의 해당 날짜**에만 나타난다. 카드에는 확인 대기가 줄어드는 것으로만 보인다.

- **표시하지 않는다**: 현재 홀, 끝날 예상 시각(ETA), 사람 수, 금액. 진행 중 여부는 기존 `gameTelemetry`의 게임 실행 상태로 이미 보인다
- 확인 대기가 **2일 이상** 남은 타석은 카드에 주황색으로 표시한다. 로그가 지워지기 전에 사람이 알아채게 하기 위해서다(§13)

### 8.2 화면 배치

- `src/lib/admin-context.ts`에 `storeRoundCounting` 추가(기존 `storeMonitorOnly`와 같은 방식: 상세 조회 열에 `agent_round_counting`을 더하고, 실패하면 기존 열만으로 다시 읽는 현재 폴백을 그대로 쓴다)
- 관찰 전용 집계 매장(삼송)의 파크 타석 카드는 송도의 관찰형 카드를 재사용한다: `observationOnly = 송도 || (storeRoundCounting && storeMonitorOnly)`. **시흥 카드는 기존 세션 카드·버튼 그대로 두고 파크 PC에만 집계 줄을 더한다.** 골프연습장 카드는 기존 60분 이용 감지를 유지한다
- 카드에는 §8.1 다섯 값을 한 줄로 요약한다. 값은 `agent_round_daily_counts`(어제~오늘 이틀)와 `agent_round_pending`(확인 대기·가장 오래된 대기 날짜)로 가져온다. 주황색 표시는 가장 오래된 대기 날짜로 판단한다. 기존 "오늘 로비 복귀" 줄은 집계 매장에서 숨긴다(시흥의 세션·이용 표시는 숨기지 않는다)
- **일별 표**: 대시보드 아래 접힌 영역 "일별 게임 수(최근 14일)". 펼칠 때만 조회한다. 행은 날짜, 열은 그 매장 타석(시흥 3, 삼송 8)의 확정 게임 수와 합계, 이어서 시작 수 합계·중도 종료·연습 건수·시간. 확인 대기가 남은 날짜는 표시한다
- 화면 갱신 주기는 송도와 같은 60초. 숨겨진 탭에서는 갱신하지 않는다(기존 `visible-poller.ts`)
- 매장관리자 계정은 자기 매장만 본다(기존 `getAdminContext` 경로를 그대로 탄다)

## 12. 하지 말 것

- 로비 복귀·플레이 시간·프로세스 종료·코스 진입만으로 게임 1회로 세지 않는다. `오늘 시작`을 게임 수라고 표시하지 않는다. 연습 시간을 게임으로 바꿔 세지 않는다
- 0단계 결과 없이 홀 판정 정규식을 만들지 않는다
- 1단계에서 현재 홀·예상 종료 시각·사람 수를 만들거나 추정하지 않는다(§15)
- Agent에 요금·과금 방식 설정을 넣지 않는다. Agent 숫자로 금액을 계산해 보여주지 않는다(§1.2)
- 잠긴 로그를 우회해서 읽지 않는다. 게임 메모리·패킷·파일을 건드리지 않는다
- 게임을 강제로 끄거나 화면을 가리지 않는다
- 원문 로그, 화면 이미지, 고객 이름을 저장·전송하지 않는다
- 송도의 설정·동작·설치본을 바꾸지 않는다. 시흥은 `roundCountingEnabled` 추가와 승인된 0.10.0 단계 설치(A-02 → 3대) 외에 바꾸지 않고, 기존 동작은 D6대로 그대로다. 시흥의 이용 감지 설정은 §2 모름 8 확인 전 바꾸지 않는다. 기존 릴리스 포인터를 덮어쓰지 않는다
- 토큰·키를 문서·로그·커밋·채팅에 남기지 않는다
- 운영 DB 쓰기, migration 실행, 배포, 릴리스 게시, 기기 전원 조작은 사용자 승인 없이 하지 않는다
- 테스트를 실행하지 못했으면 통과했다고 적지 않는다

목적: "지금 몇 번 홀인지", "언제 끝날지"를 보여주는 것. 1단계 운영이 안정된 뒤 아래 **순서대로** 검토하고, 앞 단계가 성공하면 뒤 단계는 하지 않는다.

| 순서 | 방법 | 판단 기준 |
| --- | --- | --- |
| 1 | **게임 업체에 문의.** 현재 홀·라운드 시작/종료를 파일이나 API로 받을 수 있는지 | 공식 제공되면 이것만 쓴다. 가장 안정적이고 PC별 보정이 없다 |
| 2 | **실시간 로그 재조사.** `ScreenGolf.log` 등 실행 중 읽히는 파일에서 홀 전환 신호를 새로 찾는다 | 0단계 수집 결과와 추가 시험으로, 18홀 판에서 홀마다 빠짐없이 나오는 신호가 있을 때만 |
| 3 | **화면 OCR**(§6.6) | 1·2 모두 실패할 때만. 불안정하고 PC마다 보정이 필요하다는 점을 사용자에게 다시 알리고 별도 승인 |

### 15.1 업체 문의 초안 (사용자가 보낸다. 구현자는 보내지 않는다)

```text
제목: 파크골프 시뮬레이터 라운드 진행 정보 연동 문의

안녕하세요. 귀사 파크골프 프로그램(ScreenGolf)을 사용 중인 매장입니다.
매장 운영 화면에 타석별 진행 상황을 표시하려고 합니다.
아래 정보를 파일 또는 로컬 API로 받을 수 있는지 문의드립니다.

1. 라운드 시작·종료 시각 (코스명 포함)
2. 현재 진행 중인 홀 번호, 홀 시작·종료 시각
3. 라운드 종료 시 완료한 홀 수 (9홀/18홀 구분)
4. 연습 모드 여부

- 고객 이름·점수 등 개인 정보는 필요 없습니다.
- 게임 동작에 영향을 주지 않는 읽기 전용 방식이면 좋겠습니다.
- 가능하다면 형식(파일 경로·필드)과 제공 조건을 알려주십시오.
- (선택) 현재 Binaries\Win64\Logs\main_*.log 를 게임 종료 후 읽고 있는데,
  이 파일의 형식이 공식적으로 유지되는지도 알려주시면 감사하겠습니다.
```

마지막 줄은 업체 내부 로그를 읽고 있다는 사실을 알리는 것이다. 넣을지는 사용자가 정한다.
